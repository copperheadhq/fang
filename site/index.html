The language and kernel under copperhead

Write the hardware.
Let the kernel decide what is true.

A Python-embedded language for circuit boards. You author intent — typed interfaces, parameters with units, constraints. The kernel elaborates it into one canonical model, refuses anything it cannot justify, and lowers what survives into netlists, views, simulation decks, and KiCad.

# Two candidate pin pairs for the I2C peripheral.
class MCU(Part):
    i2c = I2CPort(voh_min=2.4 * V, voltage=3.3 * V)
    PB8 = Pin("PB8", role="clock")
    PB6 = Pin("PB6", role="clock")
    PB9 = Pin("PB9", role="data")
    PB7 = Pin("PB7", role="data")
    pinmap = PinMap({
        "i2c.scl": ["PB8", "PB6"],
        "i2c.sda": ["PB9", "PB7"],
    })

class SensorBoard(System):
    mcu = MCU(package="LQFP-64")
    imu = IMU(package="LGA-14")

    def architecture(self):
        self.mcu.i2c >> self.imu.i2c

Pin assignment is a lowering result, never an authoring input. Because a choice existed, it became a decision entity naming what it rejected — so a part substitution later can be argued with rather than guessed at.

Elaboration → operation → commit

Three phases, never interleaved

The order is the whole point. A program that could observe a tool's result would not be reproducible, so it never can — it records what it wants done and stops.

PHASE 1

Elaborate

Your program runs in a sandbox with no network and only declared, hashed file inputs. It builds a graph and a tool plan. It calls no engine and touches no geometry.

A tool call returns a handle, not a result.

PHASE 2

Operate

The recorded plan runs against immutable snapshots. Placers, routers, checkers and simulators are reached across a process boundary and produce candidate realizations.

Nothing here mutates canonical state.

PHASE 3

Commit

One gate, six conditions, and the same path for a human edit, a re-elaboration, a CAD import and an agent proposal. A rejection still returns its diagnostics and its diff.

Only then are downstream artifacts written.

Diagnostics

What it refuses to do

Most of the value is in the answers the kernel declines to give. Every refusal carries a stable code, a severity, and the line that caused it.

fang check sensor_board.py

sensor_board.py:31: error: UNIT-0001 le requires operands of equal dimension: V is not A

sensor_board.py:47: error: IFACE-0001 the required signal 'sda' has no candidate pin on the right side

sensor_board.py:12: error: ELAB-0005 a power_output surface does not connect to a mechanical surface

undecided: IFACE logic high margin is undecided: vih_min unknown

blocked: TXN-0002 a required check reported a blocking severity — nothing committed

Undecided is a third truth value. An unknown datasheet number makes a check undecided — never a quiet pass. Whether undecided blocks is the gate's policy decision, not the evaluator's. A dimensionally invalid expression is rejected where it is written, so it can never be stored. A missing simulator reports unsupported rather than substituting a model. An unmodelled CAD construct is named in the import report rather than dropped. Nothing is invented to make an answer available.

Install

No required dependencies. NetworkX is an optional extra for graph analysis; ngspice is an optional external simulator. When either is absent, the toolchain says so rather than working around it.

$ pip install fang The kernel, the language, and the fang command.
$ fang build board.py Elaborate, pass the gate, persist the workspace, run the plan.
$ fang check board.py Constraints, ground topology, interface compatibility.
$ fang export board.py -o board.net A KiCad netlist, byte-identical for unchanged input.
$ fang view board.py ground -o ground.svg Ground topology as intent, distinct from net equivalence.
$ fang sim board.py --analysis transient --probe "V(1)" A SPICE deck, a run, and a result that names its coverage gaps.
